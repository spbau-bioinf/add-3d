<section class="theory" markdown="1">

## Теоретические сведения
{: .section__title}

STL (от stereolithography, стереолитография) описывает поверхность детали набором треугольников. Каждая грань задана единичной нормалью и тремя вершинами, и больше в файле ничего нет: ни связей между гранями, ни цвета, ни материала, ни единиц измерения. Формат бывает текстовым (ASCII, по названию кодировки символов American Standard Code for Information Interchange) и двоичным; двоичный компактнее, поэтому системы автоматизированного проектирования (CAD, computer-aided design) обычно пишут его.

На этой странице вы прочитаете оба варианта собственной программой. Библиотеки для этого не нужны: хватит модуля `struct` из стандартной библиотеки Python.

</section>

{: .files}

Файл `pyramid.stl` текстовый, его можно открыть в редакторе кода. Это треугольная пирамида из лекции:

```text
solid triangular_pyramid
  facet normal 0 -1 0
    outer loop
      vertex 0 0 0
      vertex 1 0 0
      vertex 0 0 1
    endloop
  endfacet
  ...
endsolid triangular_pyramid
```
{: .output .output--file data-label="pyramid.stl"}

- `solid` открывает объект, `endsolid` закрывает. После слова идет имя, на данные оно не влияет.
- Каждая грань занимает 7 строк: `facet normal` с тремя координатами нормали, затем `outer loop`, три строки `vertex` и две закрывающие строки.
- Вершины перечислены против часовой стрелки, если смотреть на грань снаружи. Нормаль первой грани (0, −1, 0): грань лежит в плоскости *y* = 0 и смотрит в сторону отрицательных *y*, то есть из пирамиды наружу.
- Порядок граней в файле любой. На грань приходится 12 чисел: 3 для нормали и по 3 на вершину.
{: .checklist}

Каждое число в двоичном STL занимает 4 байта (вещественное число одинарной точности), поэтому 12 чисел грани занимают 48 байт, и еще 2 байта отведены под атрибут. Отсюда размер файла:

<div class="formula">размер = 84 + 50·<i>F</i></div>
<dl class="where">
<div><dt>где размер</dt><dd>длина двоичного файла STL, байт</dd></div>
<div><dt>84</dt><dd>заголовок (80 байт) и счетчик граней (4 байта)</dd></div>
<div><dt>50</dt><dd>байт на грань: 12 чисел по 4 байта и атрибут 2 байта</dd></div>
<div><dt><i>F</i></dt><dd>число граней, записанное в байтах 80–83</dd></div>
</dl>

Для пирамиды из лекции 84 + 50·4 = 284 байта.

Эта формула дает практический признак двоичного файла: прочитать счетчик из байтов 80–83 и сравнить 84 + 50·*F* с настоящим размером файла. Строгим доказательством формата совпадение не является, но для файлов этого занятия признак работает без ошибок.

<aside class="callout callout--warning" markdown="1">

Единиц в STL нет
{: .callout__title}

Число 10 в файле может означать 10 мм или 10 дюймов: это знает только тот, кто экспортировал модель. Проверить единицы по самому файлу нельзя, можно только заметить, что габариты неправдоподобны для этого изделия.

</aside>

### Пример 1. Функция `read_stl`
{: .example__title}

{% capture code %}
import os
import struct


def read_stl(path):
    """Читает STL (двоичный или ASCII) и возвращает список граней.

    Грань: кортеж из трех вершин, вершина: кортеж (x, y, z).
    """
    size = os.path.getsize(path)
    with open(path, "rb") as f:
        data = f.read()
    if size >= 84:
        n = struct.unpack("<I", data[80:84])[0]
        if size == 84 + 50 * n:                      # двоичный: 84 + 50·F байт
            tris = []
            for k in range(n):
                vals = struct.unpack("<12f", data[84 + 50 * k: 84 + 50 * k + 48])
                tris.append((vals[3:6], vals[6:9], vals[9:12]))   # нормаль vals[0:3] пропускаем
            return tris
    tris, loop = [], []                              # иначе текстовый (ASCII)
    for line in data.decode("ascii", errors="ignore").splitlines():   # имя после solid может быть не латиницей
        words = line.split()
        if words and words[0] == "vertex":
            loop.append(tuple(float(w) for w in words[1:4]))
            if len(loop) == 3:
                tris.append(tuple(loop))
                loop = []
    return tris


def write_stl(path, tris):
    """Записывает грани в двоичный STL; нормаль считается по порядку вершин."""
    with open(path, "wb") as f:
        f.write(b"binary STL".ljust(80, b" "))
        f.write(struct.pack("<I", len(tris)))
        for a, b, c in tris:
            u = [b[i] - a[i] for i in range(3)]
            v = [c[i] - a[i] for i in range(3)]
            n = [u[1] * v[2] - u[2] * v[1], u[2] * v[0] - u[0] * v[2], u[0] * v[1] - u[1] * v[0]]
            length = sum(x * x for x in n) ** 0.5 or 1.0
            f.write(struct.pack("<12fH", *[x / length for x in n], *a, *b, *c, 0))


if __name__ == "__main__":
    tris = read_stl("pyramid.stl")
    print("Граней:", len(tris))
    print("Первая грань:", tris[0])

<div class="analysis" markdown="1">

Разбор
{: .analysis__title}

- `read_stl` читает файл целиком в байты `data` и сначала проверяет формулу размера. `struct.unpack("<I", data[80:84])` превращает байты 80–83 в целое число без знака; `<` означает порядок байтов «младший первым», так записан STL.
- Для двоичного файла цикл идет по граням: грань `k` начинается с байта `84 + 50 * k`. Формат `"<12f"` читает 12 вещественных чисел; `vals[0:3]` нормаль, дальше три вершины. Нормаль пропускается: ее можно вычислить по вершинам, и на [task 2-4](task_2-4.html) вы увидите, почему записанной нормали не стоит доверять.
- Текстовый файл разбирается по словам: каждая строка `vertex` дает вершину, три вершины подряд образуют грань. `errors="ignore"` пропускает символы не из ASCII: русскоязычная CAD-система может записать после `solid` имя кириллицей, и без этого параметра чтение упадет.
- Грань возвращается кортежем из трех вершин, вершина кортежем (x, y, z). Это и есть «треугольный суп»: у соседних граней общая вершина записана заново.
- `write_stl` записывает двоичный STL. Она понадобится на [task 2-5](task_2-5.html); пока ее можно не разбирать.
- Двоичные числа имеют одинарную точность, поэтому координаты из `finger.stl` выглядят как `62.08449935913086`, а не `62.0845`. При выводе округляйте их форматом, например `f"{x:.2f}"`.

<div class="theory" markdown="1">

Теория к вопросу
{: .analysis__title}

**Как `struct` превращает байты в число.** Байт хранит целое число от 0 до 255. Формат `"<I"` берет четыре байта подряд и собирает из них одно целое число без знака; знак `<` задает порядок «младший байт первым», так записан двоичный STL (раздел 3). Первый байт дает единицы, второй умножается на 256, третий на 256² = 65&nbsp;536, четвертый на 256³ = 16&nbsp;777&nbsp;216:

<div class="formula"><i>N</i> = <i>b</i><sub>0</sub> + <i>b</i><sub>1</sub> · 256 + <i>b</i><sub>2</sub> · 256² + <i>b</i><sub>3</sub> · 256³</div>
<dl class="where">
<div><dt>где <i>N</i></dt><dd>число, которое возвращает <code>struct.unpack("&lt;I", data[80:84])</code></dd></div>
<div><dt><i>b</i><sub>0</sub> … <i>b</i><sub>3</sub></dt><dd>значения байтов 80, 81, 82 и 83 файла, от 0 до 255</dd></div>
</dl>

В двоичном файле в этих байтах записан счетчик граней. У `finger.stl` там байты 80, 4, 0, 0: *N* = 80 + 4 · 256 = 1104.

**Что лежит в тех же байтах текстового файла.** Текстовый STL состоит из символов, и каждый символ ASCII занимает один байт со своим кодом: перевод строки — 10 (в шестнадцатеричной записи 0x0A), пробел — 32 (0x20), цифра «0» — 48, буква «v» — 118. Отсчитаем байты `pyramid.stl` с нуля, учитывая перевод строки в конце каждой строки:

| Строка файла | Пробелов отступа | Байт вместе с переводом строки | Номера байтов |
|---|---|---|---|
| `solid triangular_pyramid` | 0 | 25 | 0–24 |
| `facet normal 0 -1 0` | 2 | 22 | 25–46 |
| `outer loop` | 4 | 15 | 47–61 |
| `vertex 0 0 0` | 6 | 19 | 62–80 |
| `vertex 1 0 0` (начало) | 6 | — | 81, 82, 83 — первые пробелы отступа |

Байт 80 — перевод строки после `vertex 0 0 0`, байты 81–83 — первые три пробела следующей строки. Подстановка *b*₀ = 10, *b*₁ = *b*₂ = *b*₃ = 32 дает 10 + 32 · 256 + 32 · 65&nbsp;536 + 32 · 16&nbsp;777&nbsp;216 = 10 + 8192 + 2&nbsp;097&nbsp;152 + 536&nbsp;870&nbsp;912 = 538&nbsp;976&nbsp;266.

**Шестнадцатеричная запись.** Один байт — две шестнадцатеричные цифры. Число записывают со старшего байта, поэтому байты файла 0x0A, 0x20, 0x20, 0x20 дают запись 0x2020200A: в записи числа байты идут в обратном порядке.

**Почему решает размер файла, а не счетчик.** `struct` не знает, текстовый файл или двоичный: любые четыре байта превращаются в число. В текстовом STL счетчика граней нет совсем: число граней равно числу блоков `facet` … `endfacet`, у пирамиды их 4 по 7 строк. Поэтому прочитанное «число» сравнивают с размером файла по формуле раздела 2:

| Файл | Размер, Б | Счетчик *F* | 84 + 50·*F*, Б | Вывод |
|---|---|---|---|---|
| `pyramid.stl` | 538 | 538&nbsp;976&nbsp;266 | 26&nbsp;948&nbsp;813&nbsp;384 (около 27 ГБ) | не двоичный |
| `finger.stl` | 55&nbsp;284 | 1104 | 55&nbsp;284 | двоичный |
| `scan_sphere.stl` | 256&nbsp;084 | 5120 | 256&nbsp;084 | двоичный |

Чтобы текстовый файл прошел проверку, четыре его символа должны случайно дать ровно (размер − 84) / 50; для файлов занятия этого не происходит.

### Задание 2. Кольцо в полтора миллиметра <span class="level level--3">Уровень 3 · применение</span>
{: .task__title}

Файл: <span class="task__file">task\_2-1\_2.py</span>

{: .output data-label="Требуемый вывод"}

<div class="theory" markdown="1">

Теория к вопросам
{: .analysis__title}

**Единиц в файле нет.** В двоичном STL после заголовка записаны только числа: 12 вещественных чисел на грань и атрибут (раздел 2). Поля «единицы» там нет. Заголовок из 80 байт — произвольный текст, программы не обязаны его заполнять и не берут из него единицы. Длина нормали равна 1 в любых единицах, потому что нормаль единичная, и о масштабе ничего не говорит. Программа, которая открывает файл, видит числа 1,42 × 1,42 × 0,32 и толкует их в своих единицах по умолчанию.

**Как заметить ошибку единиц.** Габарит сравнивают с известным размером изделия при разных предположениях о единицах:

| Если файл в … | Множитель в мм | Габариты, мм | Правдоподобно для кольца на палец? |
|---|---|---|---|
| миллиметрах | 1 | 1,42 × 1,42 × 0,32 | нет: меньше 1,5 мм |
| сантиметрах | 10 | 14,2 × 14,2 × 3,2 | сомнительно, решает внутренний диаметр |
| дюймах | 25,4 | 36,1 × 36,1 × 8,1 | да |

**Внутренний диаметр по вершинам.** Кольцо лежит плашмя, его ось вертикальна и проходит через центр габаритов. Координаты в файле: *x* и *y* от 1,29 до 2,71, поэтому ось проходит через точку (2,00; 2,00). Расстояние от вершины (*x*, *y*, *z*) до оси:

<div class="formula"><i>r</i> = √((<i>x</i> − <i>x</i><sub>c</sub>)² + (<i>y</i> − <i>y</i><sub>c</sub>)²)</div>
<dl class="where">
<div><dt>где <i>r</i></dt><dd>расстояние от вершины до оси кольца, в единицах файла</dd></div>
<div><dt><i>x</i><sub>c</sub>, <i>y</i><sub>c</sub></dt><dd>центр габаритов по <i>x</i> и <i>y</i>: (1,29 + 2,71) / 2 = 2,00</dd></div>
</dl>

Вершины кольца лежат на внутренней и наружной стенках. У вершин `ring.stl` *r* меняется от 0,39 до 0,71. Наименьшее значение — внутренний радиус: ближе к оси материала нет. Наибольшее — наружный радиус, он равен половине габарита: 1,42 / 2 = 0,71.

<div class="formula"><i>d</i> = 2 · <i>r</i><sub>min</sub> · 25,4 = 2 · 0,39 · 25,4 ≈ 19,8 мм</div>
<dl class="where">
<div><dt>где <i>d</i></dt><dd>внутренний диаметр, мм</dd></div>
<div><dt><i>r</i><sub>min</sub></dt><dd>наименьшее расстояние от оси до вершин, дюймы</dd></div>
<div><dt>25,4</dt><dd>миллиметров в дюйме</dd></div>
</dl>

Остальные размеры кольца в миллиметрах: наружный диаметр 2 · 0,71 · 25,4 ≈ 36,1 мм (это габарит), ширина обода (0,71 − 0,39) · 25,4 ≈ 8,1 мм, высота 0,32 · 25,4 ≈ 8,1 мм. Две типичные ошибки расчета: забыть умножить радиус на 2 (получится 9,9 мм, это радиус) и взять за внутренний диаметр габарит (36,1 мм — наружный диаметр вместе с ободом). При допущении «файл в сантиметрах» внутренний диаметр был бы 2 · 0,39 · 10 = 7,8 мм, при допущении «в миллиметрах» 0,78 мм; на палец подходит только вариант с дюймами.

## Итоговое задание: карточка STL-файла <span class="level level--5">Уровень 5 · итоговое</span>

**Ситуация.** Перед подготовкой к печати оператор заполняет карточку модели: формат, число граней, габариты и положение. Карточка нужна, чтобы заметить ошибку единиц до печати, а не после.

1. Если наибольший габарит меньше 5 единиц, программа печатает предупреждение с габаритами в миллиметрах в предположении, что файл в дюймах.

<div class="theory" markdown="1">

Теория к вопросу
{: .analysis__title}

**Как устроено правило «меньше 5 единиц».** Программа берет наибольший из трех габаритов и сравнивает его с порогом 5. Правило не знает, что за изделие в файле, и не знает настоящих единиц: оно сравнивает одно число с другим. Такие правила называют эвристиками: они указывают, где проверить, но ничего не доказывают.

| Модель | Наибольший габарит | Предупреждение | Верно ли оно |
|---|---|---|---|
| `finger.stl` | 40,00 | нет | да: фаланга длиной 40 мм правдоподобна |
| `ring.stl` | 1,42 | есть | да: файл в дюймах |
| `pyramid.stl` | 1 (пирамида 1 × 1 × 1 из лекции) | есть | нет: учебная модель, ошибки единиц в ней нет |

**Две ошибки эвристики.**

- *Ложная тревога:* деталь действительно мала. Пирамида 1 × 1 × 1 или деталь длиной 4 мм, правильно записанная в миллиметрах, дадут предупреждение, хотя файл исправен.
- *Пропуск:* ошибка единиц есть, а правило молчит. Модель в дюймах длиной 6 дюймов (152,4 мм) имеет габарит 6 > 5, предупреждения не будет, и слайсер получит деталь длиной 6 мм.

Кроме того, правило предлагает пересчет только из дюймов. Если бы кольцо было записано в сантиметрах, предупреждение тоже сработало бы, но предложенные 36,1 мм были бы неверны: настоящий наружный диаметр 14,2 мм.

Поэтому вывод программы — подсказка: «проверьте единицы». Решение принимает человек, который знает изделие и его настоящий размер. В STL единиц нет (раздел 2), и надежно их можно узнать только у того, кто экспортировал модель.
